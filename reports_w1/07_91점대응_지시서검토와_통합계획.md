## 2. 확인한 사실

- **우리 하네스는 이미 서버 방식이다.** `eval_proxy.py` 는 키트 `lerobot_policy.load_policy` + `policy.act`, 시작 3스텝 유지, `active_fruit_on_plate` 를 쓴다. 지시서 P0-1 은 이미 충족돼 있다.
- **성공 판정**: 같은 종류의 어느 사본이든 접시 위면 성공이다(`mdp.fruits_on_plate`).
- **`set_episode_events(spec)`** 가 받는 것은 물체별 xy 범위와 yaw 범위뿐이다(`pick_fruit.py:174-184`). 비공개 환경의 변형은 이 축일 가능성이 크다 → 스윕과 데이터에 xy·yaw·접시 범위를 넣는다.
- **te 실패의 모양**(P0-c 56회, Fable 재확인)
  - 성공은 모두 174~226스텝에 났다.
  - 실패 30회는 모두 900스텝을 다 썼다.
  - 그중 27회는 2cm 도 들지 못했다.
  - 실패한 뒤 다시 잡으러 가지 않는다 → DAgger 회복 데이터가 정확히 이 빈칸을 메운다.

## 4. 실행 연결 (자동)

```
mix3 A 생성(~13:45) ─┬─ finish_A.sh (CPU): 검증 → 합치기(scene_index) → pack → sha256·README
                     └─ run_after_A3.sh (GPU): P0 스윕 72회 → SWEEP_DONE
                          └─ run_dagger_r1a.sh: 시험 16회 → 전문가 성공 ≥ 60% → R1a (조건당 36, 저장 260에서 멈춤)
```

## 5. 데이터 품질 검증 (사용자 요청)

`quality_check.py`: 저장된 성공 에피소드의 흠을 에피소드별로 잰다.
- 팔 action 튐
- 명령 추종 오차
- 끝 정지
- 닫힘 횟수
- 쥐는 동안 과일 이동
- 쥐는 순간 손끝 오차
- 놓은 자리(접시 중심 거리)
- 같은 과일 사본 거리 차

| 데이터 | 흠 표시 | 놓은 자리 99% / 최대 | 쥐는 순간 손끝 오차 최대 |
|---|---|---|---|
| **mix3 A 딸기 165** | **1 (0.6%)**, 쥐는 동안 11.1mm 밀림 | **38 / 39mm** | 11.5mm |
| v3 400 (비교) | 10 (2.5%) | 58 / 89mm | 26.4mm |

- 기준값은 v3·A 분포를 보고 정했다. 처음 기준(팔 변화 > 6 단위, 닫힘 ≥ 2)은 정상 동작까지 잡아서 고쳤다(정상: 계획 최대 약 7.5 단위, 닫힘 2회 = 쥐기 + 끝 휴식 자세).
- 나머지 과일과 DAgger 데이터도 같은 검사를 하고, 영상 확인 시트(verify_dataset)를 본 뒤 업로드한다.

## 6. 기대효과

- P0 표와 DAgger R1a 데이터를 한 번의 GPU 사용으로 얻는다(약 7시간 절약).
- DAgger 회복 데이터가 te 의 '실패 뒤 다시 안 잡음'을 겨냥한다. 첫 시도 60% 에 재시도 두 번이 각각 50% 성공하면 90% 다 [Fable 계산, 가정].

## 7. 결론 및 추후 시사점

1. 가장 큰 위험은 GPU 없이 쓴 수집기다. 15시쯤 처음 돌 때 문제가 나올 수 있다 → 시험 16회와 60% 관문을 뒀다. 실패하면 GIF 를 보고 고친다. 18:30 까지 안 되면 GPU 를 mix3 B 생성으로 돌린다(Fable 위험 1 대응).
2. 회복 데이터가 첫 시도 성공을 깎을 수 있다. 로컬 56회에서 다음을 함께 본다.
   - 첫 시도 성공
   - 다시 잡기 성공(> 300스텝)
   - 들다 놓침
3. ★ 사용자 결정이 필요하다: 로컬 GPU 과일 전용 기간을 일 18시까지 늘릴지(지금 합의는 금 오전까지). 코비 평가가 같은 GPU 를 쓰면 수집이 멈출 수 있다.
4. 작업 중 실수: 정적 검사 도구(pyflakes) 패키지 파일이 프로젝트 폴더에 내려받아졌다. 실행하지 않았고 임시 폴더로 옮겼다.
