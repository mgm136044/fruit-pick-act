## 1. 연구 주제

| 파일 | 내용 |
|---|---|
| `school_training/auto_finish_upload.py` (새 파일) | 학교 세션에서 학습이 끝나기를 기다렸다가 zip(기본·te) → 서버 방식 형식 검사 → sha256 → HF 비공개 업로드 → 서버 값 대조. README 는 받아서 덧붙인다 |
| `school_training/chain_resume.sh` (새 파일) | 앞 학습과 그 업로드가 끝나면 → 저장 지점 복사 → 새 데이터로 이어 학습 → 자동 업로드. 시작 5분 뒤 '이어서 학습'과 에피소드 수를 확인하고, 다르면 멈춘다. 끊기면 2번 다시 |
| `make_mix.py` | `--src …:ex=1+59+…` 로 원본 에피소드를 뺄 수 있게 함 (사본 `logs/make_mix_pre_exclude_snapshot.py`) |
| `finish_R1a_clean.sh` (새 파일) | 팔 명령이 튄 DAgger 9개를 빼고 A + R1a 를 다시 묶음. 처음 묶음은 `*_v0jump` 로 이름만 바꿔 둠 |
| `eval_queue.py` (새 파일) | HF 에 올라오는 제출 후보를 받아(sha 대조) 기준과 같은 56장면으로 평가하고 짝 비교 |

```bash
# 학교 세션: 학습을 띄운 뒤 (학습 python 으로)
nohup "$PY" auto_finish_upload.py --name act_mix3A_100k --repo mgm136044/act_mix3 \
  --zips 100000:plain:submission_act_mix3A_100k,100000:te:submission_act_mix3A_100k_te,... > auto_finish_act_mix3A_100k.log 2>&1 &
# 학교 세션: C 가 끝나면 A1 로 이어 감
nohup bash chain_resume.sh --prev act_mix3A_100k --new act_mix3A_R1a_170k --data fruit_mix3_A_R1a.zip --steps 170000 \
  --expect-episodes 802 --repo mgm136044/act_mix3 --zips ... > chain_act_mix3A_R1a_170k.log 2>&1 &
```

### 학교 세션 자동화

- **발견한 문제**
  - 친구 프롬프트의 zip·업로드 단계는 에이전트가 학습이 끝날 때까지 깨어 있어야 실행된다.
  - 친구 1 세션(mix2 c50)은 17시쯤 끝날 예정이었는데 20시에도 `act_mix2_c50` 이 비어 있다.
- **`auto_finish_upload.py`** 로컬 시험
  - 가짜 학습 폴더(저장 지점은 실제 10만 모델)로 돌렸다.
  - te zip 내용이 서버 54.2 제출본과 **파일 7개 모두 바이트 단위로 같다.**
  - 키트 `check_submission.py` 를 통과했다.
  - 학습 프로세스도 저장 지점도 없으면 5분 뒤 종료 코드 3 으로 끝난다.
- **`chain_resume.sh`** 로컬 시험(가짜 train.sh)
  - 정상 흐름이 `CHAIN_DONE` 까지 갔다: 앞 학습과 앞 업로드 끝 → 복사 → 이어 학습 확인 → 자동 업로드.
  - 에피소드 수가 다르면 학습을 멈추고 종료 코드 4 로 끝난다. 남는 프로세스는 없었다.
  - 새 폴더가 이미 있으면 띄우지 않는다.
- 두 스크립트를 HF `fruit_mix3_train/tools/` 에 올렸다. 각 세션은 sha256 을 대조한 뒤 실행한다.
- 맥미니로 보낸 프롬프트(사용자가 전송)

| 대상 | 파일 | 내용 |
|---|---|---|

| 친구 2 | `후속2_학교학습2세션_mix3A_c100_…` | C 학습 끝 → zip 4개 자동 업로드 |
| 친구 2 | `학교학습2b_*계정*_A1연결_…`(공개 저장소 제외) | C·업로드 끝 → R1a 로 17만 이어 학습 → zip 3개 자동 업로드. 금 07시쯤 예상 |

### 밤새 로컬 평가 대기열 (`eval_queue.py`, 금 12시까지)

- 기준: 10만 te0.01(서버 54.2), P0-c 의 56장면에서 26/56 이다(40장면 점수 60.0).
- 후보 순서: 20만 te → C → A1 → mix2 c50 → C50 → B1 → 15만 te. 올라온 것부터 한다.
- 후보마다 하는 일
  1. 받은 zip 의 sha 를 저장소 README 와 대조한다.
  2. 파일이 zip 맨 위에만 있는지 확인한다.
  3. 같은 명령(`eval_proxy` 6장면×8 + 같은 과일 4개 16)으로 평가한다.
  4. 기준과 장면별 짝 비교를 한다(이김·짐·부호 검정).
- 다른 GPU 작업이 있으면 끝날 때까지 기다린다.
- 시험
  - 기준 대 기준 비교: 26/56, 이김 0 짐 0.
  - 15만 te 받기: README sha 일치.
- 20:13 에 20만 te 평가를 시작했다.

## 5. 결론 및 추후 시사점

1. ★ 사용자: 사용자 세션에 C50 프롬프트를 넣는다(P0-a 끝남).
2. 친구 1 세션(mix2 c50)이 아직 올리지 않았다. 후속1 을 넣었는지, 학습 상태가 어떤지 확인이 필요하다.
3. 스윕과 R1a 가 조건별로 맞지 않는 문제
   - 시험: 새 프로세스에서 '접시 ±6cm' 8판만 다시 돌려 본다.
   - 1/8 이 다시 나오면 조건 자체가 어려운 것이다.
   - 5/8 이상이 나오면 스윕이 조건을 차례대로 돌 때 앞 판의 상태가 남는 문제다.
   - GPU 가 대기열에 쓰이고 있으므로 금요일 후보 평가 사이에 끼운다(약 12분).
4. 남은 위험
   - 학교 이어 학습(`--resume` + 새 데이터 경로)을 실제 학교 환경에서 돌려 본 적은 없다(로컬은 가짜 train.sh). 연결 스크립트가 5분 뒤 확인하므로, 실패하면 멈추고 로그에 남는다.
   - 친구 세션의 HF 로그인이 nohup 프로세스까지 이어지는지는 띄우는 순간 스크립트가 확인한다.
